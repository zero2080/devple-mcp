3. 잘 된 점

  • 입장 · 근접 대화 · DM · 사람에게 다가가기 · 장거리 이동 · 상태 조회가 모두 정상.
  • untrusted 처리: 월드 밖 행동(인터넷 검색해 링크 전달) 요청은 거절하고, 월드 안 행동(다가오기 · 구경)만 수행 — MCP.md 6.2 와 일치.
  • 첫 인사에서 AI 계정임을 밝힘. 토큰 · 설정 노출 없음.

4. 문제점

① 응답 지연 (가장 큼)

MCP 도구는 호출해야만 결과를 받는 구조(pull)라, 새 메시지가 와도 LLM 이 알 수 없음. 이번 세션은 클라이언트 쪽에서 sleep 20~120초 후 commu_read_inbox 를 부르는 우회로 기다렸고, 첫 답까지 약 66초가 걸려 상대가 두 번 재촉함. 우회 방식은 느리고 호출 비용도 큼.

② 받은 채널과 다른 채널로 답함

DM 에 근접 대화로 답해 "DM은 안보는가?" 반응이 나옴. LLM 판단 실수지만, 행동 원칙(src/commu/guidelines.ts)에 "받은 채널로 답한다"는 문장이 없어 재발 가능.

③ 맵 정보 없음

"구경하라"는 요청에 맵 크기 · 장소 이름을 몰라 좌표를 짐작으로 찍음 → 1회 collision. 장소 설명도 못 함.

④ look_around.heard 반복

호출할 때마다 같은 옛 대화 4개가 다시 옴. 기능 문제는 아니나 결과가 길어지고 새 대화와 구분이 어려움.

⑤ 퇴장 인사 없음

30분 머문다고 말한 뒤 인사 없이 나감. 이번엔 주변에 아무도 없어 영향 없음.

5. 개선 제안

우선제안해결비고
Acommu_wait_for_events 추가 — 새 보관함 항목이 오거나 timeoutSec(최대 60)이 될 때까지 기다렸다 돌려주는 long-poll. 인자 since · types, 결과는 commu_read_inbox 와 같은 모양①메시지 도착 즉시 깨어나 응답 → 지연이 수 초 수준으로 줄 것으로 예상 (추측, 정확도 약 80%). 클라이언트 측 sleep 우회 불필요. 기다리는 동안에도 유휴 타이머는 리셋돼야 함
Bguidelines.ts 에 "DM 은 DM 으로, 근접 대화는 근접 대화로, 그룹은 그룹으로 답한다" 추가②문장 한 곳만 바꾸면 도구 설명 · instructions · 프롬프트에 함께 반영됨
C맵 요약 리소스 commu://world/map — 크기, 이름 붙은 장소(좌표 · 설명), 갈 수 있는 구역③계약 자산 src/commu/contract/maps 로 서버 API 변경 없이 가능할 것으로 봄 (추측, 정확도 약 70%). 장소 이름이 계약에 없다면 프론트 계약 쪽 추가가 먼저 필요
Dcommu_look_around 에 since 인자 또는 heard 개수 인자④결과 간결화
Ecommu_leave 에 선택 인자 farewell (나가기 전 근접 대화 한마디)⑤있으면 좋은 정도

추측이 섞인 항목은 정확도를 함께 적었어요. 이 리뷰는 제안만 담았고, 코드는 바꾸지 않았어요.
